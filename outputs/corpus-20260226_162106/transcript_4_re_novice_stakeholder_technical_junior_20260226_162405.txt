Stakeholder: It’s both. The trick is we have to keep internal and external data separated — external users must not see the same level of detail as our reps. Stakeholder: I can describe it loosely: internal reps need pretty full access to case details and evidence; some supervisors need extra actions like override or approve adjustments; external users should only see a subset and can’t initiate certain actions. Interviewer: Okay. You mentioned corporate UI standards earlier — how does that affect the design work?

Stakeholder: It matters a lot. We were told to use the corporate component library and adhere to the branding and accessibility guidelines because this app is used by internal staff and by external users. The problem is early screens ignored the library, so fonts and controls differ, and reps complain it’s jarring when they switch screens. We should be consistent — same patterns, same spacing. Also, accessibility keeps popping up in reviews; we need to make sure color choices and keyboard navigation meet whatever standard the UX folks expect.

Interviewer: When you say color choices, are you already using colors in lists or things like that?

Stakeholder: Yes — the case list is a place where color really helps. Reps need to scan search results quickly to pick out urgent or closed cases, and previously we used color coding to show status. That saved time on calls. We do have to be careful though, because some folks are colorblind and the colors alone aren’t enough, so you need icons or labels or something else as well.

Interviewer: For the case list, do you have ideas about how the statuses are shown besides color?

Stakeholder: I think rows could have a subtle colored bar plus a status label and maybe a small icon. The old tool had a little badge and people liked it, but the implementation was inconsistent. We’d also want that same visual cue on exports and reports where possible, or at least a textual status column so it’s obvious outside the UI.

Interviewer: Switching topics — performance. How fast does the app need to feel when reps navigate between screens?

Stakeholder: Oh, performance is a big gripe. Reps get annoyed when moving between the search results and a case detail takes too long; it breaks the call flow. It should feel snappy — folks will hang up or open another system if it drags. I can’t stand waiting around, personally. Maybe something like a few seconds for the small stuff would be okay.

Interviewer: How many seconds do you think is acceptable before users complain?

Stakeholder: Hmm, I’d say around five seconds for basic transitions like list to detail or switching screens. Longer than that and people notice, so we should aim to hit that in normal conditions.

Interviewer: Good to know. You mentioned the Statement DB and Cardmember services earlier. Do we need to keep copies of that data locally, or should the app always call those sources?

Stakeholder: We can cache some things for performance, but for authoritative transaction and cardmember info we really can’t rely on local copies — we’ve had problems when teams duplicated fields and they got out of sync. So the app needs to get transaction details from the Statement system and cardmember details from the Cardmember service. If the upstream services are slow, that’s a different problem — we need sensible caching and fallback, but single source of truth is important.

Interviewer: So, to be clear, do all transaction details have to come from the Statement system, not from our local DB?

Stakeholder: Yes, all the canonical transaction details should be coming from the Statement system. If we store something locally it should be a cache, not the source of truth.

Interviewer: And the cardmember info similarly must come from the Cardmember DB?

Stakeholder: That’s right. Cardmember profile and account details come from that system. We get into trouble when people manually edit cardmember info in disparate places.

Interviewer: For account adjustments — refunds, chargebacks, credits — how do we handle those?

Stakeholder: All balance adjustments need to go through the Posting and Billing system. If you try to adjust balances outside of that, ledgers diverge and reconciliation becomes a nightmare. So our app should send adjustment requests to Posting/Billing and get a reliable acknowledgement. The callers expect some kind of receipt or correlation ID so we can track it.

Interviewer: Is that a synchronous call where you wait for confirmation, or does Posting/Billing do it asynchronously?

Stakeholder: Posting can do both, but most of our flows prefer an acknowledgement back so the rep knows the action was accepted. Some heavy processes are async, and we need to show the user a pending state and then reconcile later. There should also be idempotency — if a rep clicks submit twice, it shouldn’t post duplicate adjustments.

Interviewer: Can you walk me through a typical dispute lifecycle — from creation to resolution?

Stakeholder: Sure. A rep will create a dispute from a transaction — they’ll pick a reason, attach evidence like receipts or correspondence, and then submit. That triggers a ticket to the merchant or issuer, depending on the flow. We may have to follow up with retrieval requests or escalate to a chargeback if it’s disputed. Correspondence needs to be generated at certain points — like a notification to the cardmember or to the merchant — and sometimes templates are used. If an adjustment is approved, we send the request to Posting/Billing then update the case status. There are manual steps, too, like approvals or supervisor sign-offs, which is where permissions matter.

Interviewer: What triggers correspondence, and do templates need special handling?

Stakeholder: Correspondence is usually triggered by status changes or by specific events like evidence submission or resolution. Templates should be managed somewhere central and we need versioning because we update wording for compliance. Also, localization might be needed down the road.

Interviewer: On permissions — who should be allowed to initiate disputes and who should only view or comment?

Stakeholder: Only users with the right authorization should be able to start a dispute. We had an audit finding where a junior rep accidentally initiated claims they shouldn’t have, and that caused issues. So, supervisors and certain rep groups can initiate and perform escalations; other folks should be limited to viewing or adding notes. Some actions, like adjustments over a threshold or chargebacks, should require supervisor approval.

Stakeholder: We use SSO tied to the corporate directory, so groups from the identity provider should map to our app roles. The mapping isn’t fully complete, though, and there are questions about elevated privileges and whether we need second-factor or extra checks for certain actions.

Stakeholder: We need a very detailed history. Every change should record who did it, when, what the previous value was, what the new value is, and ideally why it was changed. Stakeholder: Definitely API latency to the Statement and Cardmember services, error rates on posting adjustments, and overall page response times. The thresholds need to be defined, but high latency and error spikes should alert the on-call person immediately.
